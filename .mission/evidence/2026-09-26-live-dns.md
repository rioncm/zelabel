# Live launch timeout and DNS correction — 2026-09-26

The owner reported interface timeouts after launching ZeLabel in vnme. Read-only checks found Deployment `zelabel` at 1/1 available and pod `zelabel-79646cdd9c-pldkw` at 3/3 Ready, with Service endpoint `10.42.1.177:4180` and Ingress address `192.168.90.20`. The OIDC proxy completed discovery from Pocket ID. The TLS Secret existed.

Before the correction, `labels.vanness.life` was a CNAME to `proxy.vanness.life`, whose A record was `192.169.90.20`. A normal HTTPS request timed out. A request directed to the verified Traefik address with `curl --resolve labels.vanness.life:443:192.168.90.20 -I https://labels.vanness.life/` returned HTTP 302 to `https://id.vanness.me/authorize` with a valid certificate. This located the fault in DNS, before the app.

Using the `vnme-dns` helper under the owner's authorization, the `labels.vanness.life` CNAME was changed to `traefik.vanness.me`. The DNS API returned `status: ok`; both the household DNS server and a fresh local `dig` then resolved the name to `192.168.90.20`. The direct HTTPS test continued to return the Pocket ID redirect. No image or pod restart was required.

The Mac's system resolver still used the old `proxy.vanness.life` chain immediately after the change, so a normal `curl` continued to time out. The old CNAME had a one-hour TTL. A proposed correction of the shared `proxy.vanness.life` A record was rejected by automatic approval review because it could affect other services; that record was not changed. A local DNS-cache flush did not clear the stale system result because restarting `mDNSResponder` required a password. Clients may need their DNS cache refreshed or to wait for the cached CNAME to expire. Full authenticated login and iPhone rendering are not yet verified.

## Follow-up after owner DNS repair

The owner reported correcting the shared DNS issue. A normal, unforced `curl -I https://labels.vanness.life/` connected to `192.168.90.20` with a valid certificate and returned HTTP 302 to Pocket ID.
